# Structured Logging Strategy

## Summary

Structured logging means emitting log entries as machine-parseable data structures (typically JSON) rather than free-form text. At scale — 1 million IoT devices, dozens of services, legacy + modern systems — structured logging is non-negotiable. It enables reliable search, aggregation, alerting, and correlation. This document defines the structured logging contract for the healthcare IoT platform: the fields every service should emit, the naming conventions, the cardinality guardrails, and the migration path for legacy systems.

---

## Why Structured Logging Matters

### Unstructured Log
```
2024-01-15 10:30:45 ERROR [ingestion-service] Failed to validate device event from DEV-PM100-0042: schema mismatch in field "heart_rate" - expected int, got string. Retrying (attempt 2/3). Correlation: corr-alert-789
```

**Problems**:
- Extracting `device_id`, `error_reason`, `retry_count`, `correlation_id` requires regex
- Regex breaks when message format changes
- No consistent field names across services
- Aggregation ("how many schema mismatches today?") requires expensive text parsing

### Structured Log (JSON)
```json
{
  "timestamp": "2024-01-15T10:30:45.123Z",
  "severity": "ERROR",
  "service.name": "ingestion-service",
  "service.version": "2.4.1",
  "environment": "production",
  "region": "us-east-1",
  "k8s.namespace": "iot-ingestion",
  "k8s.pod": "ingestion-service-7b8d9f-x2k4q",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "00f067aa0ba902b7",
  "correlation_id": "corr-alert-789",
  "event_type": "device.event.validation_failed",
  "operation": "validateDeviceEvent",
  "device_id": "DEV-PM100-0042",
  "tenant_id": "HOSP-789",
  "site_id": "SITE-456",
  "message": "Schema mismatch in field heart_rate: expected int, got string",
  "error.code": "SCHEMA_MISMATCH",
  "error.field": "heart_rate",
  "error.expected_type": "int",
  "error.actual_type": "string",
  "outcome": "failure",
  "retry.count": 2,
  "retry.max": 3
}
```

**Benefits**:
- Every field is independently queryable
- Consistent across all services
- Aggregation is trivial: `count where error.code = "SCHEMA_MISMATCH"`
- No regex needed
- Machine-parseable by any log backend

## The Structured Logging Contract

This is the standardized field schema that all services (modern and transformed legacy) should emit.

### Required Fields (Every Log Entry)

| Field | Type | Description | Example |
|-------|------|-------------|---------|
| `timestamp` | ISO 8601 datetime | When the log was emitted | `2024-01-15T10:30:45.123Z` |
| `severity` | string (enum) | Log level | `DEBUG`, `INFO`, `WARN`, `ERROR`, `FATAL` |
| `service.name` | string | Name of the emitting service | `ingestion-service` |
| `service.version` | string | Deployed version | `2.4.1` |
| `environment` | string | Deployment environment | `production`, `staging`, `dev` |
| `message` | string | Human-readable log message | `Device event received` |

### Recommended Fields (Most Log Entries)

| Field | Type | Description | Example |
|-------|------|-------------|---------|
| `region` | string | Cloud region | `us-east-1` |
| `trace_id` | string | W3C trace ID | `4bf92f3577b34da6...` |
| `span_id` | string | W3C span ID | `00f067aa0ba902b7` |
| `operation` | string | Operation/function name | `validateDeviceEvent` |
| `outcome` | string (enum) | Result of operation | `success`, `failure`, `partial`, `skipped` |

### Domain-Specific Fields (When Applicable)

| Field | Type | Description | Example |
|-------|------|-------------|---------|
| `tenant_id` | string | Tenant/hospital identifier | `HOSP-789` |
| `site_id` | string | Site/facility identifier | `SITE-456` |
| `device_id` | string | Device identifier (may be hashed) | `DEV-PM100-0042` |
| `device_type` | string | Type of device | `patient_monitor` |
| `correlation_id` | string | Business transaction ID | `corr-alert-789` |
| `causation_id` | string | Causing event ID | `evt-ing-001` |
| `event_id` | string | This event's unique ID | `evt-val-002` |
| `event_type` | string | Structured event type | `device.alert.validated` |

### Error Fields (When outcome=failure)

| Field | Type | Description | Example |
|-------|------|-------------|---------|
| `error.code` | string | Machine-readable error code | `SCHEMA_MISMATCH` |
| `error.message` | string | Error detail | `Expected int, got string` |
| `error.type` | string | Exception class | `ValidationException` |
| `error.stacktrace` | string | Stack trace (truncated) | `...` |

### Performance Fields (When Relevant)

| Field | Type | Description | Example |
|-------|------|-------------|---------|
| `duration_ms` | integer | Operation duration | `45` |
| `retry.count` | integer | Current retry attempt | `2` |
| `retry.max` | integer | Maximum retries | `3` |
| `queue.depth` | integer | Queue depth at time of processing | `1500` |

### Infrastructure Fields (Added by Collector, Not Application)

| Field | Type | Description | Source |
|-------|------|-------------|--------|
| `k8s.namespace` | string | K8s namespace | k8sattributes processor |
| `k8s.pod` | string | Pod name | k8sattributes processor |
| `k8s.node` | string | Node name | k8sattributes processor |
| `k8s.container` | string | Container name | k8sattributes processor |
| `k8s.deployment` | string | Deployment name | k8sattributes processor |
| `host.name` | string | Hostname (legacy) | Resource detection |

## Severity Levels

Use a consistent severity scheme across all services:

| Level | Numeric | When to Use | Indexed? |
|-------|---------|-------------|----------|
| `TRACE` | 1 | Extremely detailed diagnostic info | No — rarely sent to backend |
| `DEBUG` | 5 | Detailed diagnostic info | Selectively — often filtered |
| `INFO` | 9 | Normal operational events | Yes |
| `WARN` | 13 | Something unexpected but handled | Yes |
| `ERROR` | 17 | Operation failed, intervention may be needed | Yes |
| `FATAL` | 21 | System is unusable | Yes + alert |

### Rules
- **Never log PHI at DEBUG/TRACE level** (it's tempting to dump payloads for debugging)
- **INFO should be the default production level** for diagnostic logs
- **Event journal entries are always INFO or higher** — they should never be filtered
- **WARN is not an error** — it means "this is unusual but the system handled it"
- **ERROR means something failed** — if you're logging ERROR, there should be an actionable response
- **FATAL means the process is about to exit** — use sparingly

## Field Naming Conventions

### Rules

1. **Use dot-separated namespacing**: `service.name`, `error.code`, `k8s.pod`
2. **Use snake_case for multi-word fields**: `correlation_id`, `device_type`, `retry_count`
3. **Use consistent prefixes**: All error fields start with `error.`, all K8s fields with `k8s.`
4. **Never use spaces or special characters** in field names
5. **Be stable**: Once a field name is published, don't rename it. Add new fields instead
6. **Be specific**: `device_id` not `id`, `tenant_id` not `org`
7. **Follow OTel semantic conventions** where they exist

### Anti-Patterns

| Bad | Good | Why |
|-----|------|-----|
| `msg` | `message` | Be explicit |
| `lvl` | `severity` | Don't abbreviate |
| `ts` | `timestamp` | Standard name |
| `err` | `error.message` | Namespaced, clear |
| `id` | `device_id` or `event_id` | Ambiguous without prefix |
| `data` | specific fields | Too generic, breaks indexing |
| `info` | specific fields | Meaningless field name |
| `metadata` | specific fields | Unstructured grab-bag |

## High-Cardinality Dangers

**Cardinality** = the number of unique values a field can have.

| Field | Cardinality | Risk |
|-------|------------|------|
| `environment` | ~3 | None |
| `severity` | ~6 | None |
| `service.name` | ~50 | None |
| `event_type` | ~200 | Low |
| `tenant_id` | ~10,000 | Medium — acceptable if you need it |
| `device_id` | ~1,000,000 | High — index carefully |
| `correlation_id` | Unbounded | Very High — essential but expensive |
| `trace_id` | Unbounded | Very High — essential but expensive |
| `user_id` | Varies | High — be careful |
| `request_body` | Unbounded | Extreme — NEVER index |
| `stacktrace` | Unbounded | Extreme — NEVER use as tag/facet |

### Rules for High-Cardinality Fields

1. **Index them** only in backends that handle high cardinality well
2. **Never use them as Datadog tags** — tags are low-cardinality (use attributes/facets)
3. **Set retention policies** — short retention reduces cardinality impact
4. **Don't facet/aggregate** on high-cardinality fields — query by exact match only
5. **Consider hashing** device_id if you don't need the raw value for querying

## Designing Logging for Different Service Types

### API/HTTP Services
- Log request received (INFO) and response sent (INFO)
- Log errors with full context (ERROR)
- Include HTTP method, path, status code, duration
- DO NOT log request/response bodies (PHI risk, cardinality)
- DO propagate and log trace_id, correlation_id

### Event Processors (Kafka Consumers)
- Log event consumed (DEBUG or INFO based on volume)
- Log event processed with outcome (INFO)
- Include kafka.topic, kafka.partition, kafka.offset
- Include correlation_id, causation_id from event envelope
- Log to event journal (separate from diagnostic)

### Background Workers / Cron Jobs
- Log job started (INFO) and completed (INFO)
- Log progress for long-running jobs (INFO, periodic)
- Include job_name, job_run_id, items_processed
- Include duration, outcome

### Legacy Services (Post-Transformation)
- Include `source.type: "legacy_transformed"` to flag provenance
- Include `transformation.confidence` to indicate parse reliability
- Include `source.file` and `source.line_number` for debugging
- Accept that some fields will be missing or approximate

## Logging Anti-Patterns

| Anti-Pattern | Problem | Fix |
|-------------|---------|-----|
| Logging entire request/response bodies | PHI exposure, cardinality explosion, cost | Log only relevant fields |
| String concatenation in log messages | Loses structure, breaks parsing | Use structured fields |
| Inconsistent field names across services | Can't query across services | Enforce shared schema |
| Using `toString()` on objects | Unstructured blobs in message field | Use specific fields |
| Logging in a loop | Volume explosion | Log summary after loop |
| Not logging errors with context | Can't debug without re-deploying | Always include operation, IDs, outcome |
| Logging sensitive data at DEBUG | PHI/PII in logs | Never log PHI regardless of level |
| Using custom log levels | Confusion, inconsistent filtering | Stick to standard 6 levels |

## Revision Summary

### Mental Model
Think of structured logging as a **database schema for your log entries**. Every log line is a row. Fields are columns. If your columns are consistent and well-typed, you can query efficiently. If every row has different columns, your "database" is useless.

### Top Use Cases
- Cross-service querying by correlation_id, tenant_id, device_id
- Automated alerting on error.code frequency
- Dashboard aggregation by service, severity, outcome
- Compliance audit via event_type queries

### Top Mistakes
1. Logging unstructured text and hoping to parse it later
2. Inconsistent field names across services (device_id vs deviceId vs DeviceID)
3. Putting PHI in debug logs
4. Indexing high-cardinality fields as tags in Datadog (use facets or attributes)
5. Not including trace_id/correlation_id on every log entry

### Tradeoff Table

| Decision | Option A | Option B | Recommendation |
|----------|----------|----------|----------------|
| Log format | JSON (verbose, parseable) | Logfmt (compact, less nested) | JSON for consistency with OTel |
| Field contract | Strict schema enforcement | Loose convention | Strict for required fields, loose for optional |
| device_id in logs | Raw value (queryable) | Hashed (privacy-safe) | Raw in production (needed for support), hashed in shared/dev |
| Stack traces | Full trace | First 5 lines | Full trace, truncated at 5000 chars |

### Quick Revision Bullets
- Structured = machine-parseable key-value pairs, not free-form text
- Required fields: timestamp, severity, service.name, service.version, environment, message
- Use dot-separated namespacing: `error.code`, `k8s.pod`, `service.name`
- High-cardinality fields (device_id, correlation_id, trace_id): index but don't tag
- Never log PHI/PII regardless of log level
- Event journal entries use the same schema but go to a separate index
- Legacy transformed logs include `source.type: "legacy_transformed"` and confidence level
- Consistent field naming across all services is more valuable than any single field
