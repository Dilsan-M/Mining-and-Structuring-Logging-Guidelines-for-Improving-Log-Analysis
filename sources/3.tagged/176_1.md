# RustPods Logging Best Practices: Technical Reference and Implementation Protocol

## Preamble: Document Scope and Relevance

This document defines the technical standards and operational protocols for logging and debugging within the RustPods application. It is intended for developers and maintainers seeking to ensure consistent, performant, and professional logging throughout the system. All recommendations and examples are current as of the latest implementation. Legacy or deprecated techniques are clearly marked.

## 1. Logging System Architecture

- **Custom Logger**: RustPods implements a custom logging system with category-based filtering and atomic flag checking.
- **Default Output**: <log_verbosity>Only warnings and errors are displayed by default, ensuring a professional user experience.</log_verbosity>
- **Selective Debugging**: <where_to_log>Developers can enable debug output for specific categories via command-line flags.</where_to_log>
- **Performance**: The system is optimized for minimal overhead when debug output is disabled.

## 2. Core Logging Principles

### 2.1 Clean Default Experience
- <log_verbosity>Application startup and normal operation display only warnings and errors.</log_verbosity>
- <log_verbosity>Debug messages are suppressed unless explicitly enabled.</log_verbosity>
- <how_to_log>All debug output must use the appropriate logging macros; `println!()` is prohibited for debug purposes.</how_to_log>

### 2.2 Category-Based Debugging
- <where_to_log>Debug output is organized into logical categories aligned with the application's architecture.</where_to_log>
- <where_to_log>Categories include: `ui`, `bluetooth`, `airpods`, `config`, `system`.</where_to_log>
- <where_to_log>Developers can enable one or more categories as needed for targeted diagnostics.</where_to_log>

## 3. Logging Macros and Usage

### 3.1 Standard Log Levels
<how_to_log>
```rust
error!("Failed to initialize Bluetooth adapter: {}", error);
warn!("Device connection unstable, RSSI: {}", rssi);
info!("Connected to AirPods: {}", device_name);
debug!("Processing {} devices from scanner", device_count);
trace!("Raw BLE data: {:?}", raw_data);
```
</how_to_log>

### 3.2 Category-Specific Debug Logging
<how_to_log><where_to_log>
```rust
crate::debug_log!("ui", "Window state changed to: {:?}", window_state);
crate::debug_log!("bluetooth", "CLI scanner found {} devices", devices.len());
crate::debug_log!("airpods", "Battery levels: L:{}% R:{}% C:{}%", left, right, case);
crate::debug_log!("config", "Loading configuration from: {}", config_path);
crate::debug_log!("system", "Application lifecycle state: {:?}", state);
```
</where_to_log></how_to_log>

## 5. Command-Line Usage Protocol

- <log_verbosity>`rustpods` (default): Only warnings and errors are shown.</log_verbosity>
- <log_verbosity>`rustpods --quiet`: Errors only.</log_verbosity>
- <where_to_log>`rustpods --debug-ui`: UI debug output enabled.</where_to_log>
- <where_to_log>`rustpods --debug-bluetooth`: Bluetooth debug output enabled.</where_to_log>
- <where_to_log>`rustpods --debug-airpods`: AirPods debug output enabled.</where_to_log>
- <where_to_log>`rustpods --debug-config`: Config debug output enabled.</where_to_log>
- <where_to_log>`rustpods --debug-system`: System debug output enabled.</where_to_log>
- <where_to_log><log_verbosity>`rustpods --debug-all` or `-v`: All debug categories enabled.</log_verbosity></where_to_log>

## 6. Implementation Requirements

### 6.1 Required Practices
- <how_to_log>Use `debug_log!` macro for all category-specific debug output.</how_to_log>
- <how_to_log><log_verbosity>Use `info!`, `warn!`, and `error!` for always-visible messages.</log_verbosity></how_to_log>
- <what_to_log>Include contextual information in all log messages.</what_to_log>
- <how_to_log>Prefer structured data over string concatenation.</how_to_log>
- <how_to_log>Use lazy evaluation for expensive debug computations.</how_to_log>

### 6.2 Prohibited Practices
- <how_to_log>Do not use `println!()` for debug output.</how_to_log>
- <how_to_log>Do not use `log::debug!` directly for category-specific output.</how_to_log>
- <how_to_log>Avoid excessive debug output in tight loops.</how_to_log>

## 9. Performance Considerations

- The `debug_log!` macro is optimized for minimal overhead when debug output is disabled.
- Atomic flag checking ensures fast runtime performance.
- <how_to_log>String formatting and expensive computations are only performed when output is enabled.</how_to_log>

## 10. Logging for Battery Intelligence System

The [Battery Intelligence System](battery_intelligence.md) is a critical subsystem requiring rigorous logging and observability. <how_to_log>All event logging, error reporting, and diagnostic output for battery analytics must conform to the standards in this document.</how_to_log>

### Logging Strategies for Battery Intelligence
- <how_to_log><where_to_log>Use the `debug_log!` macro with the `airpods` or `system` category for all significant battery events, model updates, and prediction anomalies.</where_to_log></how_to_log>
- <what_to_log>Log contextual information: device ID, event type, battery levels, timestamps, computed rates, and confidence metrics.</what_to_log>
- <what_to_log>Focus on meaningful state transitions, errors, and prediction results.</what_to_log>

### Example Log Messages
<how_to_log>
```rust
crate::debug_log!("airpods", "Battery event: 10% drop detected, device: {}, from {}% to {}%, elapsed: {} min", device_id, prev_level, curr_level, elapsed_min);
crate::debug_log!("airpods", "Depletion rate buffer updated: {} samples, median rate: {:.2} min/10%", buffer_len, median_rate);
crate::debug_log!("airpods", "Prediction: {}% remaining, estimated time-to-empty: {} min, confidence: {}", est_level, time_to_empty, confidence);
crate::debug_log!("system", "Battery intelligence model error: {}", error_msg);
```
</how_to_log>
