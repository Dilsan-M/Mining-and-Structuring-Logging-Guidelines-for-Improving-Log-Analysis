# Java — Logging Standards Fitness Function

This example enforces Java logging standards as an automated fitness function. For the full conceptual background, see [tutorial.md](../../tutorial.md).

---

## Standards enforced

### logging-rules.yml — how to log

| Rule | What it prevents |
|---|---|
| <how_to_log>No `java.util.logging`</how_to_log> | Mixed log formats; JUL bypasses SLF4J configuration |
| <how_to_log>No direct Logback imports</how_to_log> | Implementation coupling; prevents swapping the log backend |
| <how_to_log>No string concatenation in log calls</how_to_log> | Eager string allocation; use `{}` placeholders instead |
| <how_to_log>Logger typed to own class</how_to_log> | Misleading source attribution in log output |
| <how_to_log>No `System.out.println`</how_to_log> | Unstructured, unlevelled output bypassing the logger |

### required-fields-rules.yml — what to log

| Rule | Required field(s) | Triggered when |
|---|---|---|
| `http-event-missing-request-id` | <what_to_log>`requestId={}`</what_to_log> | <where_to_log>Any `request.*` event</where_to_log> |
| `http-request-completed-missing-status-code` | <what_to_log>`statusCode={}`</what_to_log> | <where_to_log>`request.completed` event</where_to_log> |
| `http-request-completed-missing-duration` | <what_to_log>`durationMs={}`</what_to_log> | <where_to_log>`request.completed` event</where_to_log> |
| `batch-event-missing-job-id` | <what_to_log>`jobId={}`</what_to_log> | <where_to_log>Any `job.*` event</where_to_log> |
| `batch-job-completed-missing-record-count` | <what_to_log>`recordCount={}`</what_to_log> | <where_to_log>`job.completed` event</where_to_log> |
| `etl-event-missing-pipeline-id` | <what_to_log>`pipelineId={}`</what_to_log> | <where_to_log>Any `pipeline.*` event</where_to_log> |
| `etl-pipeline-completed-missing-row-counts` | <what_to_log>`rowsIn={}`, `rowsOut={}`</what_to_log> | <where_to_log>`pipeline.completed` event</where_to_log> |
| `async-event-missing-message-id` | <what_to_log>`messageId={}`</what_to_log> | <where_to_log>Any `message.*` event</where_to_log> |
| `async-event-missing-queue-name` | <what_to_log>`queueName={}`</what_to_log> | <where_to_log>Any `message.*` event</where_to_log> |
| `error-log-missing-exception-or-reason` | <what_to_log>exception arg or `reason={}`</what_to_log> | <where_to_log>Any `log.error()`</where_to_log> |

## Moving from Warning to Error

Semgrep violations currently produce a **warning** — the build stays green but the summary shows a ⚠️ count. Once your team has fixed existing violations and wants to enforce the standard as a hard gate, promote it to an error:

### Step 1 — Fix all violations

```bash
semgrep --config .semgrep/logging-rules.yml src/main/ --exclude="*Bad.java"
```

Work through each finding:

- <how_to_log>Replace `java.util.logging` / Logback imports with SLF4J: `import org.slf4j.Logger; import org.slf4j.LoggerFactory;`</how_to_log>
- <how_to_log>Replace string concatenation with `{}` placeholders: `logger.info("order.started orderId={}", orderId)`</how_to_log>
- <how_to_log>Replace `System.out.println` with `logger.info("event.name")`</how_to_log>
- <how_to_log>Ensure logger is typed to its own class: `LoggerFactory.getLogger(MyClass.class)`</how_to_log>

### Step 2 — Confirm zero violations locally

```bash
semgrep --config .semgrep/logging-rules.yml src/main/ --exclude="*Bad.java"
# Expected: "Findings: 0"
```

### Step 3 — Promote to error in the workflow

In [`.github/workflows/fitness-java-logging.yml`](../../.github/workflows/fitness-java-logging.yml), change:

```yaml
        continue-on-error: true   # warning
```

to:

```yaml
        continue-on-error: false  # error — blocks the build
```

And restore the exit code:

```python
sys.exit(1 if count > 0 else 0)
```

Once merged, any new violation will fail the build and block the PR.

## SLF4J parameterised logging pattern

```java
<how_to_log>// BAD — eager string allocation
logger.info("Processing order " + orderId + " for user " + userId);</how_to_log>

// GOOD — {} placeholders evaluated lazily (only if log level is active)
<how_to_log>logger.info("order.processing_started orderId={} userId={}", orderId, userId);</how_to_log>
```

## MDC correlation context pattern

```java
// In the HTTP filter (CorrelationFilter.java)
<how_to_log>MDC.put("correlationId", correlationId);

try {
    chain.doFilter(request, response);
} finally {
    MDC.remove("correlationId");  // Always clean up in thread pools
}</how_to_log>
```

Every log line emitted during the request now carries `correlationId` automatically, regardless of which service class produces it.

## SonarQube built-in rules (complement Semgrep)

SonarQube's built-in Java rules cover additional logging anti-patterns:

| Rule | What it catches |
|---|---|
| `java:S2629` | <how_to_log>Logging args should not require evaluation (same as our Semgrep rule)</how_to_log> |
| `java:S4792` | Configuring loggers is security-sensitive |
| `java:S1166` | <how_to_log>Exception handlers should preserve original exception</how_to_log> |
| `java:S2139` | <how_to_log>Exceptions should be logged or rethrown — not both</how_to_log> |

Semgrep and SonarQube are complementary: SonarQube covers general anti-patterns across all projects, while Semgrep enforces your organisation-specific conventions <how_to_log>(SLF4J only, no JUL, MDC required)</how_to_log>.
