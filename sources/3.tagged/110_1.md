# Lemline Unified Logging Strategy

This document outlines the unified logging strategy for the Lemline project, providing guidelines for consistent logging
across all modules.

## Overview

The Lemline project uses a unified logging approach based on SLF4J with Quarkus configuration. The logging strategy is
designed to:

1. <how_to_log>Provide consistent log formats across all modules</how_to_log>
2. <what_to_log>Include contextual information in logs for better traceability</what_to_log>
3. <log_verbosity>Use appropriate log levels for different types of events</log_verbosity>
4. <how_to_log>Support structured logging for better analysis in production environments</how_to_log>

## Log Levels

The following log levels are used throughout the application:

| Level | Purpose                                                                 | Example Usage                               |
|-------|-------------------------------------------------------------------------|---------------------------------------------|
| TRACE | <log_verbosity>Very detailed information, useful for debugging complex issues</log_verbosity>          | <how_to_log>Detailed method entry/exit, variable values</how_to_log> |
| DEBUG | <log_verbosity>Detailed information on the flow through the system</log_verbosity>                     | <how_to_log>Method execution, decision points</how_to_log>           |
| INFO  | <log_verbosity>Interesting runtime events</log_verbosity>                                              | <how_to_log>Workflow started/completed, service startup</how_to_log> |
| WARN  | <log_verbosity>Potentially harmful situations that might lead to errors</log_verbosity>                | <how_to_log>Caught exceptions, retries</how_to_log>                  |
| ERROR | <log_verbosity>Error events that might still allow the application to continue running</log_verbosity> | <how_to_log>Uncaught exceptions, service failures</how_to_log>       |

## Contextual Logging

<how_to_log>The logging utility provides context-aware logging through MDC (Mapped Diagnostic Context). This allows including
contextual information in all log messages without explicitly adding it to each log statement.</how_to_log>

### Standard Context Keys

The following standard context keys are defined in `LogContext`:

<what_to_log>- `workflowId`: The workflow instance ID</what_to_log>
<what_to_log>- `workflowName`: The workflow name</what_to_log>
<what_to_log>- `workflowVersion`: The workflow version</what_to_log>
<what_to_log>- `nodePosition`: The current node position</what_to_log>
<what_to_log>- `correlationId`: A correlation ID for tracing requests across services</what_to_log>
<what_to_log>- `requestId`: A unique ID for each request</what_to_log>
<what_to_log>- `userId`: The ID of the user making the request (if applicable)</what_to_log>

### Using Context-Aware Logging

<how_to_log>To use context-aware logging, wrap your code with the `withLoggingContext` or `withWorkflowContext` functions:</how_to_log>

<how_to_log>```kotlin
// General context
withLoggingContext(
    LogContext.REQUEST_ID to requestId,
    LogContext.CORRELATION_ID to correlationId
) {
    // Your code here
    logger.info { "Processing request" }
}

// Workflow-specific context
withWorkflowContext(
    workflowId = id,
    workflowName = name,
    workflowVersion = version,
    nodePosition = position.toString()
) {
    // Your code here
    logger.info { "Processing workflow" }
}
```</how_to_log>

## Log Format

The log format is configured in `application.properties` and includes:

<what_to_log>- Timestamp with milliseconds</what_to_log>
<what_to_log>- Log level</what_to_log>
<what_to_log>- Context information (requestId, workflowId, correlationId)</what_to_log>
<what_to_log>- Logger name (class name)</what_to_log>
<what_to_log>- Thread name</what_to_log>
<what_to_log>- Message</what_to_log>
<what_to_log>- Exception (if present)</what_to_log>

<how_to_log>Example:</how_to_log>

<how_to_log>```
2023-06-15 10:15:30.123 INFO [req123,wf456,corr789] [WorkflowConsumer] (main) Processing workflow message
```</how_to_log>

## JSON Logging for Production

<how_to_log>For production environments, JSON logging can be enabled for better log analysis. This is configured in
`application.properties` but commented out by default:</how_to_log>

<how_to_log>```properties
# JSON logging for production environments
#quarkus.log.handler.json=true
#quarkus.log.handler.json.date-format=yyyy-MM-dd HH:mm:ss.SSS
#quarkus.log.handler.json.pretty-print=false
#quarkus.log.handler.json.record-delimiter=\n
#quarkus.log.handler.json.exception-output-type=formatted
#quarkus.log.handler.json.additional-field.app-name.value=${quarkus.application.name}
#quarkus.log.handler.json.additional-field.env.value=production
```</how_to_log>

## Best Practices

1. <log_verbosity>**Use the appropriate log level**: Choose the log level based on the importance and audience of the message.</log_verbosity>
2. <how_to_log>**Use lambda for log messages**: Always use the lambda syntax for log messages to avoid string concatenation when the
   log level is disabled.</how_to_log>
   <how_to_log>```kotlin
   // Good
   logger.debug { "Processing item $itemId" }
   
   // Bad
   logger.debug("Processing item " + itemId)
   ```</how_to_log>
3. <how_to_log>**Include context information**: Use the context-aware logging functions to include contextual information in logs.</how_to_log>
4. <how_to_log>**Be concise but informative**: Log messages should be concise but provide enough information to understand what's
   happening.</how_to_log>
5. <how_to_log>**Log at entry and exit points**: Log at the beginning and end of important methods to track execution flow.</how_to_log>
6. <what_to_log>**Include relevant data**: Include relevant data in log messages, but be careful not to log sensitive information.</what_to_log>
7. <how_to_log>**Use structured logging in production**: Enable JSON logging in production environments for better log analysis.</how_to_log>

<how_to_log>- Functions for setting context values for logging</how_to_log>

## Examples

### Basic Logging

<how_to_log>```kotlin
private val logger = logger()

fun someMethod() {
    logger.info { "Starting method execution" }
    // Method implementation
    logger.debug { "Processed item: $item" }
    // More implementation
    logger.info { "Method execution completed" }
}
```</how_to_log>

### Context-Aware Logging

<how_to_log>```kotlin
private val logger = logger()

suspend fun run() {
    withWorkflowContext(
        workflowId = id,
        workflowName = name,
        workflowVersion = version,
        nodePosition = position.toString()
    ) {
        logger.info { "Starting workflow execution" }
        // Workflow execution
        logger.info { "Workflow execution completed" }
    }
}
```</how_to_log>

### Error Logging

<how_to_log>```kotlin
try {
    // Some code that might throw an exception
} catch (e: Exception) {
    logger.error(e) { "Failed to process item: $itemId" }
    // Error handling
}
```</how_to_log>
