# Product Requirements Document: Podman systemd Manager

## Executive Summary

A unified container orchestration and health monitoring system that leverages systemd for managing multiple Podman pods and containers. Provides automatic health checks, intelligent restart policies, dependency management, and <where_to_log>centralized logging across all containerized services.</where_to_log>

## Problem Statement

### Current Pain Points

1. **Manual Management Overhead**
   - Multiple pods/containers require individual management scripts
   - No unified view of container health across projects
   - Manual intervention needed when containers fail
   - Startup order dependencies managed ad-hoc

2. **Lack of Health Monitoring**
   - No proactive detection of unhealthy containers
   - Issues discovered reactively when services fail
   - No automated recovery mechanisms
   - Difficult to track container uptime and reliability

3. **Poor Observability**
   - Logs scattered across multiple containers
   - No centralized monitoring dashboard
   - Hard to correlate issues across related services
   - Missing historical health metrics

4. **Inconsistent Service Management**
   - Each pod uses different management patterns
   - No standard approach to restarts and updates
   - Boot-time startup not reliably configured
   - Resource limits not systematically applied

## Goals and Objectives

### Primary Goals

1. **Unified Management Interface**

   - Continuous health checks for all services

## Feature Requirements

### Phase 1: Core systemd Integration (MVP)

#### 1.1 Service File Generation
**Priority**: P0 (Critical)

- Auto-generate systemd service files from existing pods
- Support pod-level and container-level services
- Configure dependency ordering (Requires=/After=)
- Include restart policies (on-failure, always, etc.)
- Set resource limits (memory, CPU)

**Acceptance Criteria**:
- Generate valid systemd service files for any pod
- Services start in correct dependency order
- Failed services auto-restart per policy
- Resource limits enforced by systemd

#### 1.2 Health Check Framework
**Priority**: P0 (Critical)

- Define health check methods per container type
  - HTTP endpoint checks
  - TCP port checks
  - Command execution checks
  - Custom script checks
- Configure check intervals and timeouts
- Implement systemd watchdog integration
- Support multi-stage checks (startup, readiness, liveness)

**Acceptance Criteria**:
- Health checks run automatically per interval
- Unhealthy containers restart automatically
- Health status queryable via CLI
- systemd status reflects health state

#### 1.3 Unified CLI Management
**Priority**: P0 (Critical)

Commands:
```bash
podmgr init <pod-name>           # Generate systemd services
podmgr status [pod-name]         # Show status of all/specific pod
podmgr start <pod-name>          # Start pod via systemd
podmgr stop <pod-name>           # Stop pod via systemd
podmgr restart <pod-name>        # Restart pod via systemd
podmgr enable <pod-name>         # Enable boot-time startup
podmgr disable <pod-name>        # Disable boot-time startup
<how_to_log>podmgr logs <pod-name> [container] # View logs</how_to_log>
podmgr health <pod-name>         # Check health status
```

**Acceptance Criteria**:
- All commands work for any registered pod
- Commands integrate with systemd seamlessly
- Output is clear and actionable
- Error handling provides helpful guidance

### Configuration Format

**Main Config** (`config/podmgr.yaml`):
```yaml
# Global settings
health_checks:
  default_interval: 30s
  default_timeout: 10s
  retry_attempts: 3

alerts:
  enabled: true
  channels:
    - type: discord
      webhook_url: "https://..."
    - type: email
      smtp_server: "smtp.resend.com"
      from: "alerts@example.com"
      to: ["admin@example.com"]

systemd:
  service_dir: "/etc/systemd/system"
  reload_after_generate: true

# Pod registry
pods:
  - name: secondbrain
    config: "pods/secondbrain.yaml"
  - name: n8n
    config: "pods/n8.yaml"
```

**Pod Config** (`config/pods/secondbrain.yaml`):
```yaml
name: secondbrain
description: "AI-powered personal knowledge management system"

# Startup order and dependencies
services:
  - name: ollama
    container: secondbrain-ollama
    restart_policy: always
    health_check:
      type: command
      command: "ollama list"
      interval: 30s

  - name: backend
    container: secondbrain-backend
    restart_policy: on-failure
    depends_on:
      - ollama
    health_check:
      type: http
      url: "http://localhost:5001/health"
      interval: 30s
      expected_status: 200

  - name: discord
    container: secondbrain-discord
    restart_policy: on-failure
    depends_on:
      - backend
    <how_to_log>health_check:
      type: log
      pattern: "Bot connected"
      interval: 60s</how_to_log>

# Resource limits
resources:
  ollama:
    memory_limit: "8GB"
    cpu_limit: "4.0"
  backend:
    memory_limit: "2GB"
    cpu_limit: "1.0"
  discord:
    memory_limit: "512MB"
    cpu_limit: "0.5"

# Alerts
alerts:
  critical:
    - service: backend
      condition: "down"
      channels: ["discord", "email"]
  warning:
    - service: ollama
      condition: "high_memory"
      threshold: "90%"
```

## Risks and Mitigations

| Risk | Impact | Likelihood | Mitigation |
|------|--------|------------|------------|
| systemd compatibility issues with Podman | High | Low | Test on multiple distros, document requirements |
| Health check false positives | Medium | Medium | Configurable retry logic, tunable thresholds |
| Performance overhead from monitoring | Low | Medium | Optimize check intervals, async processing |
| Breaking existing pod management | High | Low | Migration tool, backward compatibility mode |
| Complex dependency management | Medium | High | Start simple, add features incrementally |
