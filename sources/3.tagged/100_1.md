# Logging Policy

This section describes the logging policy in the Meadowlark API source code. In
general, this policy seeks to balance the goals of providing sufficient
information for an administrator to understand the health of the system and
understand user interaction with the system with the equally important goals of
protecting sensitive data and avoiding excessive log storage size.

## Logging Principles

<how_to_log>* Use structured logging for integration into log-monitoring applications
  (LogStash, Splunk, CloudWatch, etc.).</how_to_log>
<what_to_log>* Do not log sensitive data.</what_to_log>
<log_verbosity>* Use an appropriate log level.</log_verbosity>
<what_to_log>* Include a correlation / trace ID wherever possible, with the ID being unique
  to each HTTP request.</what_to_log>
<what_to_log>* Provide enough information to help someone understand what is going on in the
  system, and where, but</what_to_log>
<how_to_log>* Be careful not to make the log entries too large, thus becoming a storage
  problem.</how_to_log>
<where_to_log>* Logs will be written to the console, at minimum.</where_to_log>
<how_to_log>* If any transformation or business logic is necessary for writing an info or
  debug message, use the utility `IsDebugEnabled`  and `IsInfoEnabled` functions
  first before executing that logic.</how_to_log>

## Log Levels

<log_verbosity>Project Tanager applications will utilize the following levels when logging
messages. These levels help the reader to understand if any remedial action is
needed, and they allow the administrator to tune the amount of data being
logged.</log_verbosity>

* `FATAL`
  <log_verbosity>* The application should shut down after logging a message, if possible.</log_verbosity>
  * Applies when:
    * System is unable to startup.
  * Response:
    * Investigate in detail. Is there a service down? Is there an application bug?
    * Submit a bug report with the Ed-Fi team if appropriate, through the [Ed-Fi
      Community Hub](https://success.ed-fi.org).
* `​ERROR`
  <log_verbosity>* Applies when:
    * Something unexpected occurred in code, which interrupts service in some
      way, or
    * An error occurred in an external service, for example, a database server
      was down.</log_verbosity>
  * Response:
    * Submit a bug report with the Ed-Fi team if appropriate, through the [Ed-Fi
      Community Hub](https://success.ed-fi.org).
    * Investigate the external service; report error to service provider if
      applicable
* `WARN`
  <log_verbosity>* Applies when:
    * Something unexpected occurred in code, but the system is able to recover
      and continue.</log_verbosity>
  * Response:
    * If you see this happening frequently, consider submitting a detailed
      report in the [Ed-Fi Community Hub](https://success.ed-fi.org). There may
      be an opportunity for improving the code and/or providing better error
      handling for the situation.
* `INFO`
  <log_verbosity>* Applies when:
    * Displays information about the state of an HTTP request, for example,
      which function is currently processing the request.</log_verbosity>
  * Response:
    * Generally, none required.
* `DEBUG`
  <log_verbosity>* Displays additional information about the state of an HTTP request and/or
    state of responses from external services.</log_verbosity>
  <what_to_log>* Includes anonymized HTTP request payloads for debugging integration
    problems.</what_to_log>

> [!TIP] Anonymized Payloads
> <what_to_log>When vendor API clients encounter data integration
> failures, the support teams often want to know about the failed payload, and this
> information is not always readily available from the maintainers of the client
> application. Providing anonymized payloads meets the support need "half way"
> in that the system administrator and/or a support team member can see
> the _structure_ of the messages sent, without being able to see the
> detailed _content_. In many cases, this will be sufficient to understand why a
> request failed.</what_to_log>

## Examples

These examples are general guidelines and not 100% exhaustive.

### Fatal

<log_verbosity>* Missing required configuration information
* Out of memory or disk space</log_verbosity>

### Error

<log_verbosity>* Unhandled null reference
* Database connection / transaction failure after exhausting retry attempts</log_verbosity>

### Warning

<log_verbosity>* A database connection / transaction failure occurred, but was recovered with
  an automatic retry</log_verbosity>

### Informational

<what_to_log>* Received an HTTP request
  * URL
  * clientId
  * traceId
  * verb
  * contentType
  * _do not include the payload_</what_to_log>
<what_to_log>* Responded to an HTTP request
  * URL
  * response code
  * clientId
  * duration from time of receipt of HTTP request to response (milliseconds)
  * _do not include the payload_</what_to_log>
<what_to_log>* Process startup and shutdown</what_to_log>
<what_to_log>* Database created</what_to_log>

### Debug

<what_to_log>* Received an HTTP request → add anonymized payload</what_to_log>
<how_to_log>* Replace potentially sensitive string and numeric data with `null`  before
    logging.</how_to_log>
<how_to_log>* Could hard code restrictions to "known-to-be-sensitive" attributes, for
    example attributes on Student, Parent, and Staff.</how_to_log>
* However, that could fall short with a change to the data model.
<how_to_log>* Therefore, it will be safest to replace all string and numeric data.</how_to_log>
<how_to_log>* One potential exception: descriptors.
    * descriptor values will never contain sensitive data;
    * since the other string and numeric values are anonymized, the descriptor
      value itself does not provide a side channel to sensitive information;
    * there is value to having this when debugging failed HTTP requests.</how_to_log>
<what_to_log>* Responded  to an HTTP request → add payload</what_to_log>
<how_to_log>* Will require anonymization of the natural key fields when reporting a
    referential integrity problem</how_to_log>
<what_to_log>* Entered a function</what_to_log>
<what_to_log>* About to connect to a service or run through an interesting algorithm</what_to_log>
<how_to_log>* Received information back from a service
  * Metadata only</how_to_log>
