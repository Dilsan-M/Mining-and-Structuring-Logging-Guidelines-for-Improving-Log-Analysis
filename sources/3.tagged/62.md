_This document builds collaboratively through step-by-step discovery. Sections are appended as we work through each architectural decision together._

## Project Context Analysis

### Requirements Overview

**Functional Requirements:**
The product defines 13 functional contracts spanning the full polyrepo operation lifecycle:

- Workspace discovery and confirmation before mutation (FR-001)
- Dependency relationship visibility across direct and transitive paths (FR-002)
- Deterministic cascade planning with risk/approval checkpoints (FR-003)
- Trackable cascade execution with explicit per-step states (FR-004)
- Approval/trust controls with operator override and approver audit data (FR-005)
- Resume from consistent checkpoint and guided recovery on failure (FR-006, FR-007)
- Fast workspace health/status and historical operation review at scale (FR-008, FR-009)
- Drift detection with prioritization and decision queue workflows (FR-010, FR-011)
- Stable automation/scriptability contracts for CI and non-interactive use (FR-012)
- Safe migration and compatibility-check workflows across versions (FR-013)

Architecturally, this implies distinct capability areas for discovery, graph/planning, orchestration, approvals, recovery, status/history, drift intelligence, and automation interfaces.

**Non-Functional Requirements:**
Quality constraints materially shape architecture:

- Performance: status responses under 3s p95 for up to 50 repos; graph/planning and queue operations with bounded latency.
- Reliability and recovery: high cascade success rates, interruption-safe state handling, and rapid diagnostic guidance.
- Integrity and safety: zero unacknowledged partial states, explicit authorization/approval gates for mutation.
- Auditability: complete lifecycle event capture for all mutating operations.
- Usability: first-value onboarding experience and clear operational messaging.
- Scalability envelope: read-path support up to 100 repos without degradation.
- Maintainability and compatibility: high transition-test coverage, backward-compatible machine schemas within major versions.

**Scale & Complexity:**
Complexity is high due to safety-critical mutation workflows across many repositories and strong operational guarantees.

- Primary domain: CLI-first polyrepo orchestration developer tool
- Complexity level: High
- Estimated architectural components: 12

Complexity indicators:
- Real-time/near-real-time behavior: moderate (live operational status and cascade progression updates)
- Multi-tenancy needs: low in MVP (workspace-scoped operations)
- Regulatory burden: indirect but relevant (supply-chain/compliance visibility expectations)
- Integration complexity: high (Git provider APIs, CI/CD systems, local state/cache, auth/keychain)
- User interaction complexity: medium-high (decision-heavy and failure-recovery-centric flows)
- Data complexity: medium-high (dependency DAG + durable operation history + compensation/resume state)

### Technical Constraints & Dependencies

- Git hosting state is authoritative for mutable operations; local state supports orchestration, audit, and resilience.
- All mutations must be bounded by explicit plan/preview and confirmation policies.
- Safe automation boundaries are mandatory (allowed/confirmed/prohibited classes of actions).
- Recovery must be idempotent and checkpoint-based; resume behavior cannot duplicate or corrupt operations.
- Operational interfaces must support both human-readable and stable machine-readable outputs.
- Configuration and schema evolution must be explicit, validated, and migration-safe.
- UX and operational behavior must satisfy desktop-first, keyboard-first execution with responsive fallback and accessibility gates.

### Cross-Cutting Concerns Identified

- Trust and governance: approval controls, autonomy boundaries, and operator override pathways.
- Security posture: token handling hygiene, scope validation, and redaction of sensitive values.
- Resilience: interruption handling, compensation logging, checkpoint resume, and conflict detection.
- Observability: status/health telemetry, operation history, audit completeness, and actionable error contracts.
- Interoperability: CI/CD coexistence, stable CLI/JSON contracts, and check-mode semantics.
- Consistency: deterministic planning, explicit state models, and schema/version compatibility discipline.
- Accessibility and usability: WCAG 2.2 AA, keyboard completeness, semantic state communication, and clear remediation UX.

## Starter Template Evaluation

### Primary Technology Domain

CLI tool (Rust) with secondary desktop shell support, based on project requirements analysis.

### Starter Options Considered

1. Official Cargo scaffold (`cargo init` / `cargo new`)
- Best fit for CLI-first architecture and multi-crate workspace design.
- Uses Rust-native conventions and lowest abstraction overhead.
- Easiest to enforce strict domain boundaries (`core`, `github`, `cli`, `tauri`) from day one.
- Maintained directly by Rust tooling docs and ecosystem standards.

2. `cargo-generate` template-based starters
- Faster initial scaffolding for CI/scripts/layout when a trusted template exists.
- Good for standardization, but introduces third-party template coupling.
- Less deterministic unless template governance is controlled.

3. Tauri-first scaffold (`create-tauri-app`)
- Strong official bootstrap for desktop UX surfaces.
- Better for desktop-first apps, less aligned to this project's CLI-first MVP priorities.
- Still valuable as a later secondary bootstrap for the desktop crate/shell.

### Selected Starter: Official Cargo Workspace Scaffold (CLI-First)

**Rationale for Selection:**
This project's architecture and requirements are CLI-first, safety-critical, and heavily domain-driven. The Cargo-native scaffold gives maximum control over crate boundaries, test strategy, state/recovery design, and machine-output contracts without inheriting assumptions from desktop-first templates. It also matches the PRD's crate architecture direction and keeps future Tauri integration additive rather than foundational.

**Initialization Command:**

```bash
mkdir constellation
cd constellation
cargo init --name constellation --vcs git --bin .

mkdir crates
cargo new crates/constellation-core --lib --vcs none
cargo new crates/constellation-github --lib --vcs none
cargo new crates/constellation-cli --bin --vcs none
cargo new crates/constellation-tauri --bin --vcs none
```

**Architectural Decisions Provided by Starter:**

**Language & Runtime:**
Rust 2024-edition packages by default (`cargo new`/`cargo init` defaults), enabling a Rust-first domain and CLI runtime model.

**Styling Solution:**
N/A for CLI foundation. Desktop UI styling is deferred to the `constellation-tauri` implementation track.

**Build Tooling:**
Cargo-native build/test workflow (`cargo check`, `cargo test`, `cargo clippy`, `cargo build`) as the default engineering loop.

**Testing Framework:**
Rust built-in test harness as baseline (`cargo test`), with room for layered unit/integration/contract expansion.

**Code Organization:**
Workspace-oriented crate decomposition enabling explicit boundaries:
- `constellation-core` for pure domain logic
- `constellation-github` for provider/integration layer
- `constellation-cli` for command surface and output contracts
- `constellation-tauri` for secondary desktop shell concerns

**Development Experience:**
Fast local iteration with Cargo tooling, deterministic dependency management, straightforward CI integration, and strong fit for TDD and contract-first CLI development.

**Note:** Project initialization using this command should be the first implementation story.

## Core Architectural Decisions

### Decision Priority Analysis

**Critical Decisions (Block Implementation):**
- Rust workspace architecture using Cargo scaffold from Step 3.
- Core crate boundaries:
  - `constellation-core` (domain logic, no I/O)
  - `constellation-github` (provider/integration adapters)
  - `constellation-cli` (command surface + output contracts)
  - `constellation-tauri` (secondary desktop shell)
- Data persistence and state model:
  - SQLite local state with `rusqlite` (`0.38.0`)
  - WAL mode enabled
  - Explicit state tiers (authoritative remote, derived local, local-owned durable state)
- Git provider integration strategy:
  - GitHub-first via `octocrab` (`0.49.5`)
  - REST + GraphQL hybrid usage
  - ETag-based conditional polling + local cache fallback
- CLI contract stability:
  - Versioned machine-readable envelope
  - Explicit exit code contract
  - Deterministic command behavior for automation
- Security baseline:
  - PAT auth for MVP
  - OS keychain-backed secret storage
  - Scope validation + global output redaction
  - Explicit approval gates for mutating operations

**Important Decisions (Shape Architecture):**
- Runtime/tooling baseline:
  - Rust stable (`1.93.1` channel at verification time)
  - `clap` (`4.5.60`) for command parsing
  - `tokio` (`1.49.0`) for async orchestration
  - `petgraph` (`0.8.3`) for dependency graph modeling
  - `tauri` (`2.10.2`) and `@tauri-apps/cli` (`2.10.0`) as secondary interface path
- Error model:
  - Typed domain errors in core
  - Context-wrapped application errors in adapters/CLI
  - User-facing what/why/fix rendering pattern
- Caching approach:
  - Endpoint-specific TTL policy
  - Cache invalidation on config/hash changes
- CI/CD strategy:
  - GitHub Actions cross-platform build/test gates
  - schema/contract checks in CI

**Deferred Decisions (Post-MVP):**
- Multi-provider adapters (GitLab/Bitbucket/Azure DevOps)
- Webhook-first event ingestion replacing polling for all flows
- Full web dashboard/API product surface
- Advanced enterprise policy/RBAC layers beyond MVP trust controls

### Data Architecture

- Database: SQLite (`rusqlite 0.38.0`) as workspace-local durable state and cache.
- Data modeling:
  - Operation-centric model with lifecycle states and compensation records.
  - Explicit checkpoint/resume semantics for idempotent recovery.
- Validation:
  - Strict startup validation of workspace config.
  - Batch diagnostics (report all config issues in one pass).
- Migration approach:
  - Numbered idempotent migrations executed on startup with rollback-on-failure semantics.
- Caching strategy:
  - ETag/If-None-Match for GitHub REST polling.
  - TTL cache policies by endpoint class (status, repo metadata, limits).

### Authentication & Security

- Authentication method:
  - PAT for MVP with required-scope checks at startup.
- Authorization patterns:
  - Three-tier automation boundary:
    - Free (read-only)
    - Confirmed (mutations with explicit approval)
    - Prohibited (unsafe operations)
- Secret handling:
  - OS keychain storage only.
  - No token persistence in logs, config files, DB records, or PR artifacts.
- Data encryption approach:
  - Rely on OS keychain encryption for secrets; SQLite stores non-secret operational state.
- API security strategy:
  - Pre-flight permission and workspace compatibility checks.
  - Fail-fast behavior on unsupported protection/merge configurations.

### API & Communication Patterns

- API design:
  - CLI-first contract as primary external interface.
  - JSON output envelope versioned as public compatibility surface.
- Git provider communication:
  - `octocrab 0.49.5` with REST + GraphQL hybrid:
    - REST for conditional status polling/caching
    - GraphQL for batched state reads
- Error handling standards:
  - Stable error taxonomy and actionable what/why/fix output.
- Rate limiting strategy:
  - Budget-aware request scheduling + backoff/jitter for transient failures.
- Internal service communication:
  - Trait-driven ports/adapters between domain and infrastructure.
  - Event emission for async progress/state updates (CLI and desktop consumers).

### Frontend Architecture

- MVP focus:
  - CLI is the primary product interface; no UI dependency for core capability delivery.
- Secondary desktop architecture:
  - Tauri shell around shared Rust core.
  - React-based UI surface when desktop stories begin:
    - `react 19.2.4`
    - `@tanstack/react-query 5.90.21`
    - `cytoscape 3.33.1` (+ `react-cytoscapejs 2.0.0`) for graph visualization
- Routing/state/performance:
  - Desktop UI contract is defined now (implementation may phase later): canonical lifecycle states (`pending`, `running`, `waiting`, `completed`, `failed`), keyboard-first interactions, WCAG 2.2 AA compliance gates, and responsive breakpoints (320-767px, 768-1023px, 1024px+).
  - Required component contracts for desktop surfaces: status matrix, decision queue, lifecycle timeline, and recovery panel with explicit what/impact/next-action messaging.
  - UI state models consume shared core contracts to prevent drift between CLI and desktop semantics.

### Infrastructure & Deployment

- Hosting strategy:
  - Local-first executable distribution for CLI/desktop.
- CI/CD pipeline:
  - GitHub Actions build/test/release pipeline with cross-platform targets.
- Environment configuration:
  - Explicit precedence model (flags > env > workspace config > user config).
- Monitoring/logging: <what_to_log>Structured operational events with audit completeness for mutating actions.</what_to_log>
- Scaling strategy:
  - Repository-count scaling primarily through cached reads, bounded mutation concurrency, and deterministic orchestration.

### Decision Impact Analysis

**Implementation Sequence:**
1. Establish Rust workspace + crate boundaries and dependency direction.
2. Implement config model, validation, and precedence.
3. Implement SQLite schema + migrations + operation lifecycle persistence.
4. Implement GitHub provider adapter and API budget/cache controls.
5. Implement graph planning and cascade orchestration with checkpoint/resume.
6. Implement CLI command contracts, output schema, and error taxonomy.
7. Add CI quality gates for contracts, compatibility, and reliability.
8. Add desktop shell integration as secondary interface (post core stability).

**Cross-Component Dependencies:**
- Recovery/resume semantics depend on data model + migration stability.
- Automation safety depends on auth scope checks + explicit command contract.
- Performance targets depend on cache policy + API strategy + graph computation.
- Scriptability guarantees depend on output schema stability + exit code contract.
- Desktop UX consistency depends on preserving domain decisions in shared Rust core.

## Implementation Patterns & Consistency Rules

### Pattern Categories Defined

**Critical Conflict Points Identified:**
10 areas where AI agents could make different choices and produce incompatible outputs:
1) naming conventions, 2) crate/module boundaries, 3) test placement, 4) API response shape,
5) error taxonomy, 6) state/event naming, 7) logging field schema, 8) request correlation,
9) config/migration layout, 10) validation timing and ownership.

### Naming Patterns

**Database Naming Conventions:**
- Tables: `snake_case` plural nouns (e.g., `cascade_steps`, `compensation_logs`).
- Columns: `snake_case` (e.g., `workspace_id`, `created_at`, `updated_at`).
- PK/FK:
  - Primary keys: `id` (TEXT UUID/ULID or INTEGER by table decision).
  - Foreign keys: `<referenced_entity>_id` (e.g., `cascade_id`).
- Indexes: `idx_<table>_<column_list>` (e.g., `idx_cascade_steps_workspace_id_status`).
- Constraints: `ck_<table>_<rule>` / `uq_<table>_<column_list>`.

**API Naming Conventions:**
- CLI command groups and subcommands are kebab-case words (e.g., `cascade plan`, `config show`).
- JSON payload fields are `snake_case` for cross-language stability.
- Route parameter style (if HTTP surface added later): `/{resource}/{id}` with lowercase plural resources.
- Correlation header standard: <how_to_log>`x-request-id`</how_to_log>.

**Code Naming Conventions:**
- Rust modules/files: `snake_case` (`cascade_engine.rs`, `config_loader.rs`).
- Rust types/traits/enums: `PascalCase` (`CascadePlan`, `GitProvider`).
- Functions/variables: `snake_case`.
- Constants/statics: `SCREAMING_SNAKE_CASE`.
- React components (desktop UI): `PascalCase` file + symbol names.
- TypeScript vars/functions: `camelCase`; exported types/interfaces: `PascalCase`.

### Structure Patterns

**Project Organization:**
- By capability + layer, not by technical type dump:
  - `constellation-core`: domain entities, planning, policies, contracts.
  - `constellation-github`: provider adapter implementations only.
  - `constellation-cli`: command parsing, rendering, exit-code mapping.
  - `constellation-tauri`: desktop shell wiring and IPC handlers.
- Shared contracts/interfaces live in `constellation-core`.
- Adapter crates cannot introduce domain business rules.

**File Structure Patterns:**
- Migrations: `crates/constellation-core/migrations/NNNN_<name>.sql`.
- Config docs/schemas: `docs/reference/`.
- Test fixtures: `tests/fixtures/` by crate.
- Command docs/help snapshots: `docs/cli/` (if generated).

### Format Patterns

**API Response Formats:**
- All machine-readable outputs use envelope:
  - `version`, `command`, `timestamp`, `data`, `warnings`.
- Success and error both preserve envelope shape.
- No ad-hoc command-specific top-level wrapper variants.

**Data Exchange Formats:**
- JSON field naming: `snake_case` only.
- Date/time: RFC 3339 / ISO-8601 UTC strings (`...Z`) at interfaces.
- Durations/latency in integer milliseconds.
- Booleans: native `true/false`; no `0/1` booleans in JSON API.
- Optional fields: explicit `null` only when semantically meaningful; otherwise omit.

### Communication Patterns

**Event System Patterns:**
- Event names: dot-separated lowercase domains (`cascade.started`, `cascade.step_failed`, `workspace.synced`).
- Event payloads require:
  - `event_name`, `event_version`, `occurred_at`, `request_id`, `workspace_id`, `actor`.
- Event versions are integer and increment on breaking payload change.

**State Management Patterns:**
- State transitions are explicit enum/status transitions; no implicit state mutation.
- Transition functions return typed outcomes (`Ok(next_state)` / typed error).
- State updates are append-first for auditability (history preserved).
- Recovery logic must be idempotent and checkpoint-aware.

### Observability & Logging Patterns

**Wide Event Strategy:**

- Build context throughout execution, emit once on completion/failure.
- Sub-step debug traces are optional internal diagnostics; canonical event is mandatory.</how_to_log>

**Logger Configuration:**
<how_to_log><where_to_log>- Single shared logger initialized once at process startup.
- Rust logging stack uses `tracing` + structured JSON formatter.
- Logger module location: `crates/constellation-cli/src/logging.rs` (and reused by tauri binary entry).</where_to_log></how_to_log>

**Middleware Logging Infrastructure:**
<how_to_log>- CLI command execution wrapper creates/propagates request context and emits final wide event.
- Handlers append business context to request-scoped context object; they do not emit scattered logs.</how_to_log>

**Request ID Correlation:**
<how_to_log>- Request ID generated at command boundary if absent.
- Accept upstream `x-request-id` when present and valid; otherwise generate.
- Propagate request ID through provider calls and all emitted events/logs.</how_to_log>

### Process Patterns

**Error Handling Patterns:**
- Domain errors are typed and non-UI-specific in core.
- Adapter/transport layers map domain errors to stable error codes.
- User-facing errors follow What/Why/Fix structure.
- All mutating failures write durable failure context before returning.

**Loading State Patterns:**
- Long-running operations expose explicit progress states:
  - `pending`, `running`, `waiting`, `completed`, `failed`.
- Progress updates are monotonic and queryable.
- Resume operates from first incomplete checkpoint only.

### Enforcement Guidelines

**All AI Agents MUST:**
- Follow naming, envelope, and field-schema rules exactly.
- Keep business logic in `constellation-core`; adapters remain integration-only.
- <how_to_log>Emit canonical wide events with required context fields.</how_to_log>
- Preserve idempotent state transitions and checkpoint-safe recovery behavior.
- Add/maintain tests for state transition and contract changes.

**Pattern Enforcement:**
- PR checklist includes pattern compliance section.
- CI checks:
  - JSON schema contract tests
  - migration naming/ordering checks
  - <how_to_log>lint rules for prohibited logging patterns</how_to_log>
  - state-transition coverage checks
- Violations logged in architecture decision notes and fixed before merge.
- Pattern updates require architecture doc amendment and affected test updates.

### Pattern Examples

**Good Examples:**
- <what_to_log>`event_name: "cascade.apply_completed"` with full context and `duration_ms`.</what_to_log>
- Migration file: `0012_add_compensation_log_index.sql`.
- JSON result envelope with `version`, `command`, `timestamp`, `data`, `warnings`.
- Core trait in `constellation-core`, concrete GitHub adapter in `constellation-github`.

**Anti-Patterns:**
- <how_to_log>`println!("something happened")` without request/workspace context.</how_to_log>
- Adding GitHub HTTP calls directly inside core domain planning code.
- Returning one command's JSON as raw array while others use envelope.

### Architectural Boundaries

**API Boundaries:**
- External boundary 1: CLI commands in `crates/constellation-cli/src/commands/*`.
- External boundary 2: Tauri IPC commands in `crates/constellation-tauri/src-tauri/src/commands/*`.
- Integration boundary: GitHub API via `crates/constellation-github/src/client/*`.
- Contract boundary: all machine-readable output shape owned by `constellation-core/src/contracts/output_envelope.rs`.

**Component Boundaries:**
- Domain rules live only in `constellation-core`.
- Infrastructure adapters live only in `constellation-github`.
- Rendering/argument parsing live only in `constellation-cli`.
- UI-only concerns live only in `constellation-tauri/ui`.

**Service Boundaries:**
- Core services expose use-case APIs (`discover_service`, `status_service`, `cascade_*_service`, `history_service`, `doctor_service`).
- Adapters implement core ports (`git_provider`, `state_store`, `keyring_provider`).
- CLI and Tauri compose services via dependency injection at startup.

**Data Boundaries:**
- Authoritative remote state: GitHub.
- Durable local operational state: SQLite state store adapter.
- Cached remote responses: SQLite cache adapter with ETag/TTL policy.
- Domain layer accesses persistence only through ports.

### Integration Points

**Internal Communication:**
- `cli` and `tauri` call core services through strongly typed use-case interfaces.
- `core` calls ports; adapters satisfy ports at runtime.
- Event contracts from core are emitted via CLI logger and Tauri event bridge.

**External Integrations:**
- GitHub REST/GraphQL via Octocrab.
- OS keychain via keyring adapter.
- CI pipelines via GitHub Actions workflows.
- Optional Tauri desktop shell for operator UI.

**Data Flow:**
- Read flow: GitHub → github adapter/cache → core service → CLI/Tauri output.
- Mutation flow: CLI/Tauri command → core policy checks → github adapter writes → state store checkpoint update → output/event emission.
- Recovery flow: state store checkpoint + compensation log → core resume logic → adapter reconciliation with GitHub.

### File Organization Patterns

**Configuration Files:**
- Root toolchain/build config at repo root.
- Runtime/user/workspace config schemas in `core/config`.
- Human reference docs in `docs/reference`.

**Source Organization:**
- Capability-first modules in core.
- Adapter-specific code isolated in github crate.
- Transport/presentation isolated in cli and tauri crates.

**Test Organization:**
- Unit/property/contract tests near owning crate.
- Cross-crate end-to-end tests under `/tests/e2e-cli`.
- Shared fixtures under `/tests/fixtures`.

**Asset Organization:**
- Desktop UI assets in `crates/constellation-tauri/ui/src`.
- Static docs assets under `docs/` only.
- No runtime business assets outside crate ownership boundaries.

### Development Workflow Integration

**Development Server Structure:**
- `cargo run -p constellation-cli` for primary workflow.
- `cargo run -p constellation-tauri` plus `ui` dev server for desktop workflow.
- Workspace-level checks/lints run from root.

**Build Process Structure:**
- Workspace build orchestrated by root Cargo workspace.
- Contract/schema checks run in CI against CLI JSON outputs and migrations.
- Release packaging split by target (CLI binary + optional Tauri installers).

**Deployment Structure:**
- CLI artifacts published per target OS/arch from release workflow.
- Tauri installers generated from `constellation-tauri/src-tauri`.
- Docs and runbooks versioned with releases.
