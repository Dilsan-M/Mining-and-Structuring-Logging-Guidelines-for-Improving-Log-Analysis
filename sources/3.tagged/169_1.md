# Logging conventions
<how_to_log>OpenKilda code is expected to use [SLF4J](https://www.slf4j.org/) as API facade for logging.</how_to_log>

### Logging Strategy
The goal is to build a diagnostics toolkit that will give enough information for diagnosing and solving 
the customer problem or system failure.

<what_to_log>The following is to be logged:</what_to_log>
<what_to_log>* Business operations with the context</what_to_log>
<what_to_log>* Transitions (workflow transition, switch state or flow status)</what_to_log>
<what_to_log>* Integration points (calls, availability)</what_to_log>
<what_to_log>* Resources availability (limit reached)</what_to_log>
<what_to_log>* Service availability (startup, shutdown)</what_to_log>

### Levels
<log_verbosity>Ensure that log messages are appropriate in content and severity:</log_verbosity>
<log_verbosity>* **debug** detailed information on the flow through the system (REST request/response, TCP packets). 
            Require no action from the support team.</log_verbosity>
<log_verbosity>* **info** important/useful runtime events (service start/stop, configuration details, event causing spinoff processes, 
            scheduled execution, requests sent to external API). 
            Require no action from the support team.</log_verbosity>
<log_verbosity>* **warn** runtime situations undesirable or unexpected, but not necessarily "wrong", anything that can potentially 
            cause application oddities, resumable errors (retrying an operation, use of deprecated APIs, 
            misuse of API, missing secondary data). 
            Require to assess potential consequences and apply mitigation measures.</log_verbosity>
<log_verbosity>* **error** runtime error fatal to the operation but not to service/application 
            (cant open a required file, missing data). 
            Require urgent intervention from a sysadmin or developer.</log_verbosity>
<log_verbosity>* **fatal** critical/severe error forcing a shutdown of service/application, 
            risk of data loss/corruption (db connection error). 
            Require immediate action from a sysadmin or developer.</log_verbosity>

### Logging of system entities
<what_to_log>* Never log sensitive data, like user credentials.</what_to_log>
<how_to_log>* Endpoint (switch ID and port) must be logged using underscore as a separator, e.g.: ``` 00:00:00:00:00:00:00:01_2 ```</how_to_log>
<how_to_log>* Always override toString() to give a good representation of the object.</how_to_log>

### Logging of system errors and exceptions
<how_to_log>* Logging of exceptions with severity WARN, ERROR or higher must be supplied with the exception stacktrace,
e.g.```log.error("Unable to read a configuration", ex);```</how_to_log>

### Best practices
<how_to_log>* Avoid multi-line log messages.</how_to_log>
<how_to_log>* Supply logging context or message with correlationId or other unique identifiers (IDs), this is tremendously helpful 
    when debugging or performing root cause analysis.</how_to_log>

### Antipatterns
<how_to_log>* Avoid the log and throw practice. As this results in multiple log messages for a single problem in the code. 
Either log the exception, or throw it, but never do both. e.g. ```catch (SomeException ex) { log.error("some message", ex); throw ex; }```</how_to_log>

<how_to_log>* Destructive Wrapping. Losing the stacktrace by wrapping the original exception is always wrong.
e.g. ```catch (SomeException ex) { throw new AnotherException("some message: " + ex.getMessage()); }```</how_to_log>
